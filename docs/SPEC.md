# ТЗ: плагін «Бюджет» для Standard Notes

Версія ТЗ: 0.2 · 2026-11-01 (додано розділ 7 «Безпека», хостинг, модель загроз)
Макети: канвас «Бюджет — макети плагіна» (десктоп, телефон, вигляд без плагіна).
Репозиторій: `alstdev/budget-sn-plugin` (**публічний** — див. 7.7).

---

## 1. Мета

Редактор-плагін для однієї нотатки «Бюджет <рік>», який:

- веде борги, накопичення, щомісячні надходження/витрати і план (шаблон місяця);
- підтримує кілька валют без автоматичного перерахунку: сума у валюті + сума в грн, введена вручну;
- зберігає все **звичайним Markdown**, який читається і редагується без плагіна (Plain Editor / Markdown);
- однаково придатний на десктопі й телефоні;
- розширюється новими типами розділів («шаблонами») без змін у вже існуючих.

## 2. Обмеження платформи (перевірено за джерелами)

| Факт | Наслідок для проєкту |
|---|---|
| Плагін-редактор вантажиться в iframe і бачить лише поточну нотатку; доступу до інших нотаток і файлів немає. | Вся БД — в одній нотатці. Зв'язків між нотатками немає. |
| Текст нотатки — завжди рядок; окремо є метадані (`appData`) під власним ключем. | Дані — у тексті (Markdown), службові налаштування UI — у метаданих. |
| Без debounce SN шифрує й зберігає нотатку на кожне натискання; рекомендовано 250–400 мс. | Debounce 300–400 мс, плюс мінімізація зайвих збережень. |
| Прев'ю за замовчуванням — перші 50 символів тексту; можна задати своє. | Плагін завжди виставляє власне прев'ю. |
| `ext.json`: `identifier`, `name`, `content_type: "SN\|Component"`, `area: "editor-editor"`, `version`, `url`, `download_url` (zip для десктопа), `latest_url` (автооновлення). | Хостинг сторінки + zip-реліз для офлайн-десктопа. |
| Кастомний плагін, встановлений за URL, може прочитати нотатку й відправити назовні. | Свій хостинг, жодних мережевих запитів (CSP), жодних CDN у рантаймі. |
| Super-нотатки зберігаються у власному JSON (Lexical), конвертація в Markdown — з втратами. | Плагін не пише у формат Super. Перенесення з Super — одноразове, вручну/скриптом. |

| GitHub Pages не дозволяє задавати власні HTTP-заголовки; CSP — тільки через `<meta>`. | CSP у `<meta http-equiv>` в `index.html`. |
| Директива `frame-ancestors` у `<meta>` не підтримується. | Захисту від вбудовування через CSP не буде; він і не потрібен — SN сам вбудовує плагін в iframe. Сторінка плагіна не містить даних. |

⁉️ Не підтверджено й перевіряється на етапі 0: робота кастомного плагіна в мобільному застосунку; ліміт розміру нотатки; поведінка при конфлікті редагування з двох пристроїв; з яких origin SN підвантажує CSS теми в iframe плагіна (впливає на `style-src`); чи перевіряє бібліотека-міст `event.source`/origin вхідних `postMessage`.

## 3. Етап 0 — перевірка платформи (до основного коду)

Мінімальний плагін `hello-budget`: показує прапорці платформи, довжину тексту, стан `locked`, кнопку «записати N КБ тексту».

Критерії проходження:

1. Встановлюється за URL `ext.json` і відкриває нотатку на **десктопі, вебі й телефоні** (Android та/або iOS — які в тебе є).
2. Збереження тексту працює на всіх трьох; зміни синхронізуються між ними.
3. Стрес-тест розміру: нотатка 100 КБ / 1 МБ / 5 МБ — заміряти час відкриття і збереження на телефоні.
4. Сувора CSP з 7.3 не ламає обмін з SN (обмін іде через `postMessage`, але перевіряємо фактично). Фіксуємо в `docs/SECURITY-NOTES.md`, які джерела довелося дозволити і чому (особливо CSS теми).
5. Конфлікт: редагуємо одну нотатку офлайн на двох пристроях → фіксуємо, що робить SN (копія-конфлікт чи перезапис).
6. Прочитати код обраної бібліотеки-мосту: чи перевіряє вона `event.source === window.parent` і який `targetOrigin` використовує в `postMessage`. Результат — у `docs/SECURITY-NOTES.md`; якщо перевірки немає — адаптер додає її сам (7.4).
7. Інфраструктура репо з 7.5–7.6 (CI, Dependabot, `.npmrc`, деплой) — до будь-якого коду етапу 1.

**Якщо пункт 1 провалюється на телефоні** — мобільна верстка відкладається, рішення переглядаємо разом.

## 4. Функціональні вимоги

### 4.1 Вкладки

| Вкладка | Що показує |
|---|---|
| Огляд | Залишок боргів (окремо по валютах), поточний місяць (надійшло / витрачено / залишок / після очікуваних), накопичення (по валютах), список «очікують оплати», заплановані покупки. |
| Борги | Картка на кожен борг (згортається як спойлер): залишок у валюті боргу, прогрес, історія платежів, «+ Платіж». |
| Місяці | Акордеон місяців (останній розгорнутий): підсумки, таблиці надходжень і витрат, рядки «очікує» з кнопкою «Оплатити», кнопка «Створити <наступний місяць> з шаблону». |
| Накопичення | Картка на кожне: баланс, ціль і прогрес, історія, «+ Поповнити», «− Списати». |
| Планування | Шаблон місяця: постійні витрати; заплановані покупки. |

Плюс кнопка «+ Розділ із шаблону» (діалог вибору типу розділу).

### 4.2 Операції

Кожна операція має поля: `Дата`, `Сума` (у валюті), `Вал`, `У грн`, `Коментар`; витрати — ще `Назва` і `Тип`.

- `Вал = UAH` → `У грн` заповнюється автоматично тією ж сумою.
- `Вал ≠ UAH` → `У грн` **обов'язкове**. Курс (`У грн ÷ Сума`) показується лише для довідки й ніде не зберігається.
- Підсумки в різних валютах **ніколи не складаються**. Загальні підсумки місяця рахуються тільки по `У грн`.

### 4.3 Пропозиція валюти

Поле валюти завжди видно і завжди можна змінити. Префіл:

| Контекст | Префіл |
|---|---|
| Платіж по боргу / операція з накопиченням | валюта цього боргу/накопичення |
| «Оплатити» рядок «очікує» | валюта з рядка |
| Нова витрата / надходження | остання використана в цьому типі операцій |

Список швидких валют: UAH, USD, EUR + «Інша…» (будь-який 3-літерний код ISO 4217). «Остання» зберігається в метаданих нотатки.

### 4.4 Борги

- Сума на старті + платежі руками. Відсотків не рахуємо.
- Від'ємна сума платежу = збільшення боргу (штраф, донарахування — вписуєш руками).
- Залишок = старт − сума платежів, у валюті боргу. Додатково: «сплачено в грн» (сума `У грн`).

### 4.5 Накопичення

- Додатна сума — поповнення, від'ємна — списання (на що — у коментарі).
- Необов'язкова ціль → прогрес у %.

### 4.6 Зв'язки між розділами

- «+ Платіж» по боргу і «+ Поповнити» накопичення мають галочку (за замовчуванням увімкнена) «Також записати у витрати поточного місяця». Тоді пишуться **два рядки**: у розділі боргу/накопичення і у витратах місяця з `Тип = борг` / `накоп.` та `Назва` = назва боргу/накопичення.
- Перевірка узгодженості (попередження, не помилка): рядок місяця з типом `борг`/`накоп.` без відповідного рядка (дата + назва + сума) у розділі — і навпаки — підсвічується.

### 4.7 Новий місяць з шаблону

Кнопка «Створити <РРРР-ММ>»:

1. Додає розділ `### РРРР-ММ <Назва місяця>` після останнього місяця.
2. Копіює всі `Постійні` як рядки витрат з `Дата = очікує`, порожнім `У грн`, тією ж валютою й сумою, `Тип = пост`, `Коментар = до DD.MM` (з колонки `День`; якщо день > днів у місяці — останній день).
3. Копіює заплановані покупки, у яких `Місяць` = цей місяць, як рядки «очікує» з `Тип = план`.
4. Повторне створення вже існуючого місяця заборонене.

«Оплатити» відкриває форму з префілом (назва, сума, валюта). Після збереження рядок стає звичайним. Якщо в шаблоні в колонці `Зв'язок` стоїть `борг: <назва>` / `накоп: <назва>`, автоматично додається рядок у відповідний розділ (галочка, увімкнена за замовчуванням).

### 4.8 Розділи з шаблонів (MVP)

| Шаблон | Розміщення |
|---|---|
| Борг | `## Борги → ### <назва> · <ВАЛ>` |
| Накопичення | `## Накопичення → ### <назва> · <ВАЛ>` |
| Місяць | `## Місяці → ### РРРР-ММ <Назва>` |
| Постійні витрати | `## Шаблон місяця → ### Постійні` |
| Заплановані покупки | `## Шаблон місяця → ### Заплановані покупки` |
| Довільна таблиця (етап 3) | `## <назва>` з колонками, заданими користувачем |

## 5. Формат даних (Markdown, budget v1)

### 5.1 Загальні правила

- Кодування UTF-8, переводи рядків `\n` (при читанні приймаються й `\r\n`).
- Перший рядок: `# <Назва нотатки>`; другий — маркер формату:
  `> формат: budget v1 · таблиці редагуються руками · рядки _курсивом_ рахує плагін`
  Плагін шукає підрядок `budget v1`; інша версія → запуск міграції або режим «тільки читання».
- Дати: `РРРР-ММ-ДД`. Спецзначення `очікує` для неоплачених рядків.
- Суми: десяткова **крапка**, без розділювачів тисяч, мінус — `-`. При читанні допускаються кома й пробіли (рукою вписане), при записі нормалізуються.
- Валюта: 3 великі латинські літери.
- Символ `|` у тексті клітинки екранується як `\|`.
- **Розрахункові рядки** — повний рядок у вигляді `_…_` одразу під заголовком розділу (і рядком `Початкова сума:` / `Ціль:`). Плагін їх ігнорує при читанні і перезаписує при збереженні.
- Ширина колонок вирівнюється пробілами для читабельності в Plain Editor (не обов'язково при читанні).

### 5.2 Граматика розділів

```
# Бюджет 2026
> формат: budget v1 · …

## Борги
### <Назва> · <ВАЛ>
Початкова сума: <число> <ВАЛ>
_<розрахункове>_
| Дата | Сума | Вал | У грн | Коментар |
|---|---:|---|---:|---|
| 2026-10-05 | 6000 | UAH | 6000 | платіж |

## Накопичення
### <Назва> · <ВАЛ>
Ціль: <число> <ВАЛ>            ← необов'язковий рядок
_<розрахункове>_
| Дата | Сума | Вал | У грн | Коментар |

## Місяці
### РРРР-ММ <Назва місяця>
_<розрахункове>_
#### Надходження
| Дата | Звідки | Сума | Вал | У грн | Коментар |
#### Витрати
| Дата | Назва | Сума | Вал | У грн | Тип | Коментар |

## Шаблон місяця
### Постійні
| Назва | Сума | Вал | День | Зв'язок |
### Заплановані покупки
| Назва | Бюджет | Вал | Місяць | На місяць | Статус |
```

- `Тип` (витрати): `пост`, `разова`, `план`, `борг`, `накоп.`. Невідоме значення зберігається як є і показується сірим.
- `Зв'язок`: порожньо, `борг: <назва>`, `накоп: <назва>`.
- `Статус` (покупки): `заплановано`, `куплено DD.MM`, `скасовано`.
- Порядок колонок фіксований; заголовки колонок порівнюються без урахування регістру й пробілів. Невідома додаткова колонка зберігається й показується.

### 5.3 Невідомий вміст

Будь-який текст, заголовок чи розділ, який жоден шаблон не впізнав, зберігається **байт у байт на своєму місці** і показується в UI як сирий текст (згорнутим блоком «Невідомий розділ»). Плагін ніколи не видаляє те, що не розпізнав.

### 5.4 Метадані нотатки (`appData`, ключ плагіна)

```json
{ "v": 1, "lastCur": { "exp": "UAH", "inc": "UAH" }, "ui": { "tab": "overview", "open": ["debt:Позика в USD", "month:2026-10"] } }
```

Тільки UI-зручності. Втрата метаданих не впливає на дані.

## 6. Архітектура

### 6.1 Стек

- TypeScript (strict), збірка Vite, UI на Preact (малий розмір), тести Vitest, ESLint.
- Міст до SN — **єдиний модуль-адаптер** поверх `sn-extension-api` (або напряму `@standardnotes/component-relay`); решта коду не знає, як влаштований обмін. Це дозволяє замінити бібліотеку без переписування. Вибір бібліотеки — на етапі 0 за результатами 3.6.
- Жодних рантайм-залежностей з CDN; жодних зовнішніх шрифтів; усе в бандлі.

### 6.2 Модулі

```
src/
  bridge/            адаптер SN: init, onNote(text, meta, locked), save(text, preview, meta), platform
  core/
    money.ts         суми як цілі мінорні одиниці (копійки/центи) — без float
    md/              токенайзер рядків, парсер/генератор таблиць
    document.ts      Document = впорядкований список блоків: Known(templateId, model) | Unknown(raw)
    registry.ts      реєстр шаблонів
    validate.ts      перевірка узгодженості зв'язків (4.6)
  templates/
    debts/  savings/  months/  monthTemplate/  (customTable/ — етап 3)
  ui/
    App, Tabs, Overview, cards, forms (OperationForm з вибором валюти), layout desktop/mobile
  styles/            змінні теми SN + власні токени
tests/
  fixtures/*.md      еталонні нотатки
```

### 6.3 Інтерфейс шаблону

```ts
interface SectionTemplate<M> {
  id: string;                         // 'debt', 'savings', 'month', …
  formatVersion: number;
  match(h: Heading, parent?: Heading): boolean;
  parse(block: MdBlock): { model: M; issues: Issue[] };
  serialize(model: M): string;        // канонічний Markdown розділу
  summary(model: M): string[];        // розрахункові _рядки_
  create(input: CreateInput): M;      // для діалогу «+ Розділ»
  views: { Card: Component<M>; Compact?: Component<M> };
}
```

Новий шаблон = нова тека в `templates/` + один рядок у `registry.ts`. Ядро не змінюється.

### 6.4 Цикл роботи

1. SN надсилає нотатку → `parse` усього тексту → `Document` + список `issues`.
2. Користувач змінює дані в UI → оновлюється модель → `serialize` → debounce 350 мс → `save(text, preview, meta)`.
3. Прев'ю нотатки: `Борги: 60 000 ₴ + 500 $ · Жовтень: залишок 6 067 ₴`.
4. Якщо нотатка змінилась ззовні (інший пристрій) — повторний `parse`; незбережені локальні правки не губляться: якщо є конфлікт, показуємо попередження й не перезаписуємо без підтвердження.

## 7. Безпека і захист даних

### 7.1 Модель загроз

Що захищаємо: вміст фінансової нотатки (суми, борги, контрагенти). SN шифрує нотатку на пристрої, але **всередині iframe плагін бачить її розшифрованою**. Отже плагін — точка, де дані найлегше вкрасти.

| Загроза | Як реалізується | Захист |
|---|---|---|
| Витік через мережу | `fetch`/XHR/WebSocket/`sendBeacon`/картинка-маячок з даними в URL | Жодного мережевого коду; CSP `connect-src 'none'`, `img-src 'self' data:`; лінт-заборона; перевірка в CI (7.5) |
| Витік у сховище браузера | `localStorage`/IndexedDB/cookie в iframe — дані лежать **нешифровано** поза SN | Заборонено для будь-яких даних; UI-стан — тільки в `appData` нотатки (шифрується SN) |
| Витік у логи | `console.log(text)` — потрапляє в DevTools, звіти про помилки, скриншоти | Логування вмісту нотатки заборонене; у продакшн-збірці `console.*` вирізаються |
| XSS через вміст нотатки | Рукою вписаний `<img onerror=…>` у клітинку → виконання JS в iframe | Тільки текстовий рендер; заборона `innerHTML`, `dangerouslySetInnerHTML`, `eval`, `new Function`; CSP `script-src 'self'` |
| Підроблені повідомлення | Чужий фрейм надсилає `postMessage`, підміняючи «нотатку» або отримуючи відповідь | Адаптер приймає повідомлення тільки від `window.parent` (7.4) |
| Ланцюжок постачання | Скомпрометований npm-пакет або GitHub Action | Мінімум залежностей, lockfile, `ignore-scripts`, затримка нових версій, pin по SHA (7.5) |
| Злам репо/деплою | Хтось пушить шкідливу версію → SN підтягує її з `url` при наступному відкритті і **читає нотатки** | Захист гілки, деплой тільки з тегу через ручне підтвердження, 2FA на акаунті (7.6) |
| Реальні дані в публічному репо | Справжня нотатка як фікстура, скриншот, текст issue | Тільки вигадані дані; `.gitignore`; секрет-сканінг (7.7) |
| Втрата даних | Помилка парсера перезаписує нотатку порожнім/обрізаним текстом | 7.2 |

### 7.2 Цілісність даних

- **Канонічна стабільність:** `serialize(parse(x)) == x` для канонічного тексту; для рукописного — відмінності лише в нормалізації чисел і вирівнюванні.
- Рядок, який не розібрався → `issue` + підсвітка; рядок зберігається як є.
- Розділ з критичною помилкою → «тільки читання» для цього розділу; збереження решти дозволено лише якщо цей розділ серіалізується незмінним (сирим).
- Порожній результат серіалізації або зменшення тексту більше ніж на 30% за одне збереження без явної дії видалення → збереження блокується, показується попередження.
- `locked` (Prevent editing) → увесь плагін у режимі читання.
- Видалення операцій/розділів — тільки через підтвердження в UI.
- Плагін не зберігає нотатку, доки не завершився перший успішний `parse` отриманого від SN тексту (жодного «порожнього стану за замовчуванням» поверх реальних даних).
- Перший запуск — тільки на копії нотатки.

### 7.3 Content Security Policy

`<meta http-equiv="Content-Security-Policy">` у `index.html`, стартова політика:

```
default-src 'none';
script-src 'self';
style-src 'self';
img-src 'self' data:;
font-src 'self';
connect-src 'none';
object-src 'none';
base-uri 'none';
form-action 'none';
```

- Жодних inline-скриптів і inline `<style>`; стилі — тільки CSS-файли бандла (класи). Динамічні значення (ширина прогрес-бару) — через `<progress>` або CSSOM (`el.style.x = …`), а не атрибут `style` у розмітці.
- ⁉️ CSS теми SN: якщо на етапі 0 з'ясується, що SN вставляє в iframe `<link>` на тему з іншого origin, дозволяємо **конкретний** origin у `style-src` і документуємо в `docs/SECURITY-NOTES.md`. `'unsafe-inline'` і `*` заборонені.
- Будь-яке послаблення CSP — тільки окремим PR з обґрунтуванням.

### 7.4 Міст до Standard Notes (iframe / `postMessage`)

- Увесь обмін — тільки в `src/bridge/`. Решта коду не викликає `postMessage` і не слухає `message`.
- Вхідні повідомлення: приймаються лише якщо `event.source === window.parent`; після першого валідного повідомлення фіксується його `origin`, наступні з іншим origin ігноруються.
- Вхідні дані валідуються за схемою (типи полів, `text` — рядок, розмір у розумних межах) до передачі в ядро.
- Вихідні: `targetOrigin` — зафіксований origin батька; `'*'` — тільки якщо бібліотека/платформа не дає іншого (десктоп-застосунок може мати нестандартний origin) і це задокументовано в `docs/SECURITY-NOTES.md`.
- Плагін не відкриває вікна, не робить навігацію, не створює вкладених iframe.

### 7.5 Залежності, збірка, CI

- Рантайм-залежності: тільки `preact` і бібліотека-міст. Кожна нова залежність — окремий PR з обґрунтуванням, перевіркою мейнтейнерів, ліцензії, розміру.
- Версії — точні (без `^`/`~`), `package-lock.json` у репо, встановлення тільки `npm ci`.
- `.npmrc`: `ignore-scripts=true`, `save-exact=true`, `min-release-age=3` (опція є в npm з v11.10.0 — тому в `engines` вимагаємо npm ≥ 11.10; на старішому npm вона ігнорується).
- Node — поточна LTS, версія зафіксована в `.nvmrc` і `engines`.
- CI (GitHub Actions) на кожен PR: `npm ci`, typecheck, lint, тести, збірка, `npm audit --audit-level=high`, перевірка бандла на заборонені API (7.8).
- Workflows: `permissions: contents: read` на рівні файлу, підвищення — тільки в конкретному job; усі сторонні actions **закріплені повним SHA коміту**; тригер `pull_request_target` заборонений; недовірені значення (назви PR/гілок) — тільки через `env:`, не через `${{ }}` усередині `run:`.
- Dependabot для `npm` і `github-actions` (оновлення pin-ів SHA).
- У продакшн-збірці: мінімізація, вирізання `console.*` і `debugger`, без `eval`-подібних трансформацій; sourcemap дозволено (код публічний, секретів не містить).

### 7.6 Хостинг і реліз

- Хостинг: GitHub Pages з цього репо, деплой через GitHub Actions (job має лише `pages: write`, `id-token: write`).
- Деплой **тільки з git-тегу** `v*` і **через environment з ручним підтвердженням** (required reviewer — власник). Пуш у `main` сам по собі нічого не публікує.
- Причина: веб і мобільний SN вантажать плагін з `url` при відкритті нотатки, тож опублікована сторінка — це код, який отримає доступ до розшифрованих даних.
- `download_url` для десктопа — zip конкретного тегу; у реліз додається `SHA256SUMS`.
- `latest_url` (автооновлення) на етапі 4 — вирішуємо окремо; за замовчуванням оновлюємо вручну.
- Ручні налаштування власника (не код): захист гілки `main` (PR обов'язковий, заборона force-push), 2FA на GitHub, secret scanning + push protection, Dependabot alerts, Pages source = GitHub Actions, environment `github-pages` з required reviewer.

### 7.7 Публічний репозиторій

- **Жодних реальних фінансових даних** у репо: фікстури, тести, скриншоти, приклади в документації, тексти issue/PR, повідомлення комітів. Фікстури — тільки вигадані суми й назви, файли починаються з коментаря `<!-- FICTIONAL TEST DATA -->`.
- Справжню нотатку для локальної перевірки тримати поза репо або в `local/` (є в `.gitignore`).
- Секретів проєкт не потребує взагалі (немає API, ключів, токенів). Якщо колись з'являться — тільки GitHub Secrets.

### 7.8 Автоматичні перевірки безпеки

- ESLint: `no-restricted-globals` / `no-restricted-properties` / `no-restricted-syntax` для `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `navigator.sendBeacon`, `localStorage`, `sessionStorage`, `indexedDB`, `document.cookie`, `eval`, `Function`, `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `document.write`, `window.open`; заборона `dangerouslySetInnerHTML`.
- Скрипт CI сканує зібраний `dist/` на ті самі ідентифікатори (ловить і те, що принесли залежності); винятки — явний allowlist з поясненням.
- Тест, що `index.html` містить очікувану CSP.
- Юніт-тести 7.2: порожній/обрізаний текст не зберігається; невідомий вміст переживає збереження байт у байт; XSS-рядки з клітинок рендеряться як текст.

## 8. UI

- Брейкпоінт: < 640 px — мобільна розкладка (вкладки-«таблетки», нижня панель введення, плаваюча кнопка «+»); інакше — десктоп (вкладки, діалоги).
- Кольори й шрифти — зі змінних теми Standard Notes, тому світла/темна тема працюють автоматично.
- Числа — `tabular-nums`, формат відображення `uk-UA` (пробіл тисяч, кома десяткова).
- Доходи/витрати розрізняються не тільки кольором, а й знаком `+`/`−`.
- Цілі дотику на телефоні ≥ 44 px; поля сум — `inputmode="decimal"`.
- Доступність: справжні `button`/`input`/`label`, `aria-expanded` на спойлерах, `role="dialog"` на формах.

## 9. Тестування

- Юніт: `money`, токенайзер, парсер/генератор таблиць, кожен шаблон.
- Round-trip на еталонах `tests/fixtures/` (включно з рукописними правками, кома в числах, зайві пробіли, невідомі розділи, `\|`).
- Перевірка, що невідомий вміст переживає збереження байт у байт.
- Ручний чек-лист на копії нотатки: десктоп, веб, телефон; офлайн-правка; `locked`.
